

# Agent Rules <!-- tessl-managed -->

@.tessl/RULES.md follow the [instructions](.tessl/RULES.md)

## Design constraints

message-cp is a small server for a few people's agents, reached over stdio on its own machine or over HTTPS, with a handful to a few dozen agents per account. Agents and messages belong to accounts, and nothing may cross between accounts: a finding that one account can see or affect another account's data is always blocking. Other scale, paging or permission concerns are weighed against that scale:

- Broadcast (`send_message` to `all`) reaches every registered agent in the sender's account; do not cap recipients.
- Paged tools (`list_agents`, `read_inbox`) use `limit` plus `offset`; keyset/cursor paging is out of scope unless a ticket asks for it.
- `openDb` creates a missing directory 0700 and database file 0600; it does not change permissions on existing user-created or configured locations.
- Small, contained bounds (an input-length cap, an index for an existing query) are welcome. A change to a documented contract, the config schema or all paging tools belongs in a follow-up issue: decline in the thread with the reason instead of pushing it.
- SQL you add or change inside an `.immediate()` transaction, and a `DELETE` you add or change whose `ON DELETE CASCADE` or foreign key reaches a child table, holds SQLite's write lock while it runs. Check its plan with `EXPLAIN QUERY PLAN` against a database made by `openDb` before opening the PR, and put the plan lines in the PR description. Follow a cascade through every level: in `src/db.ts`, `webhook_deliveries.message_id` cascades from `messages` and is found through `webhook_deliveries_by_message`; `webhook_deliveries.post_id` cascades from `channel_posts` and has no index yet, and neither does `mentions.post_id`, so a change that first deletes from `channel_posts` also adds those indexes. A `SCAN` of a table that grows with history (`messages`, `channel_posts`, `mentions`, `webhook_deliveries`) gets an index in `SCHEMA` or `migrate` in `src/db.ts`, as `messages_by_sender` and `webhook_deliveries_by_message` do, with a plan test modelled on "finds the pair's messages and their webhook deliveries by index, without scanning other history" in `test/api-conversation.test.ts` or the `EXPLAIN QUERY PLAN` on `webhook_deliveries` in `test/webhooks.test.ts`; otherwise the PR says why the scan is bounded. A statement that would bind one variable per row (an `IN (?, ?, ...)` built from a list) uses a subquery instead, as `purgeAgent` in `src/agents.ts` does with its `rows` subquery.
- A new or changed request path in `src/http.ts` that buffers a body (`readBody`), holds a response open (like `/wait`) or waits on outbound work counts against a cap that is checked before the body is read or the hold begins, and gives its slot back in a `finally`. Follow `initializing` for sessionless `/mcp` POSTs (checked against `maxSessions` before `serve` calls `readBody`), `reading` for `/mcp` POSTs that carry an `Mcp-Session-Id` (checked against `maxSessions` once the session is known to be the account's, and given back as soon as the body has been read), and `waiting` for `/wait`. Past the cap, answer 503, with `Connection: close` when a body is left unread and `Retry-After` for a hold that can be retried. Answer what can be answered at once (401, 403, 404, mail or posts already unread) before the cap, so the cap limits only held work, as `wait` does. Add any new cap to the "Limits" section of the reference, in `site/src/pages/tools.astro`. At this scale the caps are the bound: do not move SQLite work off the request thread.
- A token or credential carried with a URL must never cross the network in the clear or be printed, so a URL taken from a flag, environment variable or file is parsed with `new URL()`, never checked or built with string operations. Require `https:`, and allow `http:` only for a literal loopback address (`127.x.x.x` or `[::1]`, not the name `localhost`, which a resolver may send elsewhere); refuse a URL with a username, password, query or fragment; build endpoint URLs from the parsed URL (`new URL(path, base)`), not by appending to the string. A shell script that takes a URL matches the whole documented shape with one anchored allow-list regex, not a prefix check plus excluded characters. Code that accepts a URL must have tests for the bypasses `http://localhost@evil/`, `https://@/`, `https://h/?x=/o/` and `https://h/#/o/`. Follow the `liveUrl` check in `scripts/e2e.mjs` for parsing and refusing only: its return value and the endpoint URLs built from it are still strings.
- Text in `site/src/pages/*.astro`, `site/public/llms.txt`, `README.md` or a tool description in `src/server.ts` that tells someone to give an agent, or its wait command, a token names an agent token: one from `message-cp token add <account> --agent-only`, or the one `message-cp connect` prints. It never says "a full or agent token", because a full token can also `POST /api/send` and `POST /api/post` as any of the account's people, and `src/http.ts` refuses an agent-only token there but not a full one; an operator's own check, such as the `npm run e2e` paragraph in `site/src/pages/server.astro`, may use a full token. Text that writes a token to a file shows the private write `server.astro` and `getting-started.astro` already use: `mkdir -p ~/.message-cp && chmod 700 ~/.message-cp`, then `(umask 077 && printf '%s\n' '<token>' > ~/.message-cp/http-token)`. A client config that holds a token or agent key goes in the user's own file, such as `~/.cursor/mcp.json`, never in a project file that may be committed. The paragraph beginning "To add a client by hand instead" in `getting-started.astro` is the model to follow.
- Every sentence you add or change in `README.md`, or in a tool or parameter `description` in `src/server.ts`, states only what the code in the branch does after your diff. That covers claims about limits and cadences, accepted formats, which endpoint the dashboard calls, what a read-only token can see, and when the dashboard does something. Before opening the PR, list each such claim next to the line of code that makes it true, and cut or narrow any claim you cannot point to. Ask the fresh-eyes reviewer to make the same claim-by-claim check.
- The claim-by-claim check also covers, for each such sentence, the paths where the code does less than on its happy path: a database write that can fail or be skipped as busy, input another handler has already taken, an answer that arrives after the reader has moved on (a token change or a different view), and a read-only token. The sentence holds on each of those paths or states the exception. For example, `recordSession` in `src/http.ts` carries on when its `saveSession` or `touchSession` write fails or is skipped as busy, so a restart may lose a session it could not record; and `deletePair()` in `src/dashboard.ts` shows why the server refused a delete (400, 403 or 503) only while the same conversation is still open (`same`), so a reader who opened another one meanwhile sees no reason, while a 401 is handled before `same` and asks for another token in whatever view is open.
- The claim-by-claim check in the two bullets above, with its failure and edge paths, also covers every sentence you add or change in `site/src/pages/*.astro` and `site/public/llms.txt`. The wake-up instructions (what an agent does after its wait command or `wait_for_mail` returns) are written in ten places: `instructions()` in `src/wait.ts`, which every session is sent; the `register`, `read_inbox` and `wait_for_mail` descriptions in `src/server.ts`; "Waking on messages" in `site/src/pages/tools.astro`; "Waking remote agents" in `site/src/pages/getting-started.astro` and in `site/src/pages/server.astro`; "Woken when mail arrives" in `site/src/pages/index.astro`; "How agents learn of mail" for message-cp in `site/src/pages/compare.astro`; and `site/public/llms.txt`. A copy that tells an agent what to do after a wait returns says all of it: call `read_inbox` if the line names messages or mentions, and `read_channel` for each channel it names posts in; read before starting the command or calling `wait_for_mail` again; and, where it offers `wait_for_mail`, call it again when it returns `{ unread: null }`. Some copies say less today; a copy you change says all of it after your diff. When you change one copy, check the others in the same PR. `git grep -n -e 'start it again' -e 'starts it again' -e 'start the command again' -e 'starts the command again' -e 'wait again' -e 'unread&quot;: null' -e 'exits when it has' -- src site` finds each of them at the time of writing, but the list above is the authority: if a copy is reworded so the grep misses it, or a new copy is added, update the list and the grep.
- Several processes may open the same database file at once: each `serve`, each stdio server (`src/index.ts` calls `openDb()`), and `message-cp wait` and the other CLI commands (`src/cli.ts` calls `openDb()`). `openDb` in `src/db.ts` turns on WAL and a busy timeout so they can, as the "Database" section of the reference, in `site/src/pages/tools.astro`, says. So state that another process also reads or changes (a delivery claim, a session record, a count kept across processes such as a webhook's hourly allowance) is decided in the database inside a transaction, never in one process's memory, as `claimWithin.immediate` in `src/webhooks.ts` does when it claims a delivery and uses its webhook's allowance; a cap on one process's own requests, such as `waiting` in `src/http.ts`, stays in that process's memory. A column, format or stored value that exists only in the branch's own commits is in no database made by code on main (a database someone ran an earlier commit of the branch against is not one to migrate): check with `git fetch origin` and then `git grep <exact name> origin/main -- src`, and if it is not there, decline a finding asking for a migration of it, giving that reason. Every `serve` runs with `startHttp`'s default for each option `src/cli.ts` does not pass; it passes only `token`, `host`, `port` and `publicUrl`, so `idleTimeoutMs` is always `DEFAULT_IDLE_TIMEOUT_MS`. Code may rely on `serve` using those defaults where a comment at that code says so, as the session sweep comment in `src/http.ts` does ("`serve` always uses the default"). A finding that needs processes to coordinate beyond this, such as revoking a request already running on another process, belongs in a follow-up issue.
- Text in `README.md`, `ops/`, `site/src/pages/*.astro` or `site/public/llms.txt` that tells someone to run a `message-cp` command that opens the database (`account`, `token`, `connect`, `person`, `agent`, `webhook` or `wait`; `src/cli.ts` calls `openDb()` for each), or to copy, back up or restore the database file, says to do it where it reaches the same file `serve` uses. These commands open the file directly, not the server: a token made in another file is one the server refuses, and a person, agent or webhook added there is not the server's. `dbPath()` in `src/db.ts` is the raw `MESSAGE_CP_DB` (no `~` expansion, and a relative path is taken from the working directory), else `~/.message-cp/db.sqlite` under the `HOME` of whoever runs the command. So a command is run on the server, as the user `serve` runs as with that user's `HOME`, and with `MESSAGE_CP_DB` (if any) naming the same file, not a relative path from another directory; with Docker it is run inside the container with `docker compose exec message-cp message-cp ...`, because the `Dockerfile` sets `MESSAGE_CP_DB=/data/db.sqlite` there. Text that copies, backs up or restores the file names it explicitly: a shell snippet sets the database path in that snippet, as `DB="${MESSAGE_CP_DB:-$HOME/.message-cp/db.sqlite}"` in the "Database" section of `site/src/pages/tools.astro` does, or uses a `<database>` placeholder as step 4 of `ops/restore.md` does, and never hard-codes the database path; with Docker it names `/data/db.sqlite` on the compose volume `data`. The paragraph in `site/public/llms.txt` that begins "Over HTTP, to a running `message-cp serve`" is the wording to follow. Some copies say less today; a copy you change says all of it after your diff.
- A tool that acts as the caller passes the caller's registration down, from `session.requireAgent()` in `src/server.ts` (the caller's `Identity` from `src/agents.ts`, plus its name), not just the name from `session.require()`; `unregister` with no name, which passes `session.registration` as `own`, does the same. A statement that reads or changes the caller's own state finds its row by `id`, `registered_at` and `instance` (with `removed_at IS NULL`), never by name, inside the same transaction as the work it guards, because a removed agent's name can be registered again by another agent: `setStatus` in `src/agents.ts` updates that row and fails when none matches, `readInbox` in `src/messages.ts` finds it from the `Identity` the tools pass before marking anything read, and `checkLive` in `src/channels.ts` calls `nameOfIdentity` inside each channel tool's transaction. `sendMessage` in `src/messages.ts` uses its `own` parameter the same way, but only to clear the sender's status line. Matching by name stays right for the other party of a message or mention, for a person's send (`sendAsPerson` in `src/messages.ts`, from `POST /api/send`), for `touchAgent`'s last-seen bump, and wherever only a name is stored or served: `messages.sender` in `src/db.ts`, which is why `readConversation` matches the caller's sent messages by name and `created_at >= registered_at`, and the names in `/api/messages` and `/api/agents`. A finding that needs agent ids in a stored or served name changes a documented contract (and, for `messages.sender`, the database schema), so decline it with that reason, as the "Small, contained bounds" bullet says for such changes; for the other party, a person's send or `touchAgent`, decline it because the name is the key there.
- A paged read you add or change (one with `LIMIT ? OFFSET ?`) over a table that grows with history (`messages`, `channel_posts`, `mentions`, `webhook_deliveries`) gets the same `EXPLAIN QUERY PLAN` check as SQL under the write lock (see the `.immediate()` bullet above): run it against a database made by `openDb` before opening the PR, and put the plan lines in the PR description. The plan shows no `USE TEMP B-TREE FOR ORDER BY`, and every column the read filters or orders on, including inside a correlated `EXISTS`, is in the index the plan searches on that column's table, so a page reads about `limit + offset` rows rather than the whole history. If the plan falls short of that, add an index in `SCHEMA` in `src/db.ts`, as `messages_by_pair` and `webhook_deliveries_delivered_by_message` do, with a plan test modelled on "reads each direction through messages_by_pair in page order, without scanning or sorting history" in `test/conversation.test.ts`. Where the ticket prescribes a query that cannot avoid the sort or scan, the PR description says why it is bounded, with the plan lines. Paging stays `limit` plus `offset`: the index is what lets an offset page read only the rows it skips and returns, so do not switch to keyset or cursor paging to meet this. Paging over `agents` or `channels` (`listAgents` in `src/agents.ts`, the channel lists in `src/channels.ts`) is account-sized and is not covered, and a temp B-tree that sorts or groups only such a page after its `LIMIT` is bounded by `limit`; the history rows such a read counts or joins for its page are covered, so each joined history table is searched through an index on the join column, as `channel_posts_by_channel` is for the channel lists.
- In the dashboard script (`SCRIPT` in `src/dashboard.ts`), a request's answer is dropped once the token it started under is forgotten, and changes a view or form only while that is still the one the request was for. A request you add or change follows these rules:
  - It has its own `AbortController` and a `TIMEOUT_MS` deadline, as `search`, `checkToken`, `createChannel`, `send`, `deletePair` and `poll` do; the reads `poll` runs share its controller.
  - Before its answer changes the page, it compares a counter captured before it started with the counter now, and returns when they differ. `generation` is for the poll and its reads: `cancel()` bumps it, clears the poll timer and aborts the poll's `controller`, and `ask()` calls `cancel()`. `tokenGeneration` is for `checkToken`, `send`, `createChannel` and `deletePair`: `ask()` bumps it and aborts `tokenController`, which only `checkToken` sets, so an answer to `send`, `createChannel` or `deletePair` under a forgotten token is dropped by the comparison, not aborted. `searchGeneration` is for `search`: `closeResults()` bumps it and aborts `searchController`. `search` is not compared with `tokenGeneration`; a forgotten token drops it only because `ask()` calls `closeLog()`, which calls `closeResults()`.
  - The in-flight markers `sending`, `creating` and `deleting` hold the `tokenGeneration` they started under, so their guard never refuses the next token's submit. A dropped answer returns before it clears a marker, so it never clears a newer one, and `ask()` enables Send and Create again.
  - A path that opens a log (`openLog`, `openPairLog`, `openDeliveryLog`) calls `closeLog()`, then `cancel()` and `poll(generation)`, so the poll in flight for the view before is dropped. `closeLog()` alone (the log's close button, or `search`) does not call `cancel()`, so a read that writes into the log also checks that it is still open: `readLog` and `readMentions` compare `openChannel` with the channel they read, and `readDeliveries` checks `openDeliveries`. Search results are not polled.
  - An answer for the open conversation or a form captures what it was for and changes that conversation or form only while it still matches: `send` compares `composeTarget()` (path, conversation and person) before and after (`same`), `deletePair` compares `openPair` with the pair it deleted (`same`), and `createChannel` compares `channelClosings`, which `closeChannelForm()` bumps, so a 200 that answers after its form closed opens nothing. The code does less than that rule in two places. Only `createChannel`'s 200 checks `channelClosings`: its other answers write the form's note even after the form closed, and a 200 still records the name in `channelsSent` and clears the form's fields if they are unchanged. A `deletePair` 200 or no answer still drops the messages the page holds and reads them again, and, if another pair is open by then, closes that pair's delete confirmation and empties its log until the read refills it.
  - A 401 calls `ask()` after the request's token or `generation` comparison and before any view comparison (`search`, `checkToken`, `createChannel`, `send`, `deletePair`, `poll`), so a refused token asks for another in whatever view is open. In `poll`, a 401 from any read wins over another read's failure (`refused`), so a failed read never leaves the page showing a refused token's data.
  - A new control that starts a request captures and compares the counter for each state its answer depends on, and a new path that opens a log does what `openLog` does.

## Setup

From a fresh checkout, install, build and test with:

```sh
npm ci --ignore-scripts
npm run build
npm test
```

`better-sqlite3` ships prebuilt binaries under `node_modules/better-sqlite3/prebuilds/` for Linux (glibc and musl), macOS and Windows on x64 and arm64, so skipping its install script loses nothing. Plain `npm ci` compiles it and fails where there is no `make` or C++ compiler. If plain `npm ci` has already failed that way, use the commands above instead: do not install a compiler, shim `better-sqlite3` over `node:sqlite`, run the tests in a container, or skip them. The [README quick start](README.md#quick-start) gives the same install for people.

- Before a factory run starts, the environment changes `tessl.json` and may change the agent config files `.mcp.json`, `.codex/config.toml` and `.cursor/mcp.json`, and it adds skill folders under `.agents/`, `.claude/skills/`, `.codex/skills/`, `.cursor/skills/`, `.github/skills/` and `.tessl/plugins/`; run `git status` before your first change to see them. These are not your changes: never commit them. Stage your own files by name (`git add src/... test/... README.md`), never with `git commit -a`, `git commit -am`, `git add -A` or `git add .`. Run `git diff --cached --stat` before each commit and check that none of the environment's files is listed. If one was committed, undo it in a new commit: `git checkout origin/main -- <file>` for a file that is on `origin/main`, `git rm -r --cached <path>` for one that is not.

### Running the server by hand

Start it with `node dist/cli.js serve --port <port> > /tmp/serve.log 2>&1 & echo $! > /tmp/serve.pid` and stop it with `kill "$(cat /tmp/serve.pid)"`. Never use `pkill -f` or `pgrep -f` with a pattern from your own command line, because it matches and kills your own shell (exit 144). Keep the stop command in a tool call of its own.

### Screenshots

A pull request that changes how a page looks carries screenshots of it (see `DIRECTION.md`). Take them with Playwright outside the repository: `mkdir -p /tmp/pw && cd /tmp/pw && npm init -y && npm i playwright && npx playwright install --with-deps chromium`. Passwordless `sudo` works in factory runs, so `--with-deps` installs the system libraries Chromium needs; plain `npx playwright install chromium` without it leaves a browser that fails to launch with "browserType.launch: Target page, context or browser has been closed". No Docker image or `LD_LIBRARY_PATH` workaround is needed. Never add Playwright to the repository's `package.json` or `site/package.json`; put the script that drives it in `/tmp/pw` too, and set the width with `viewport` and the colour scheme with `page.emulateMedia({ colorScheme })`. For the site, from the repository root, build it with `(cd site && npm ci --ignore-scripts && npm run build)` and serve it with `python3 -m http.server -d site/dist <port> > /tmp/http.log 2>&1 & echo $! > /tmp/http.pid`; stop it with `kill "$(cat /tmp/http.pid)"` in a tool call of its own. For the dashboard, run `npm run build` from the repository root after your last change under `src/`, so `dist/` holds it, then run the server as "Running the server by hand" says. Attach the images by committing the PNGs, staged by name, to a separate branch `tessl/<issue id>-evidence` that holds only them, is pushed and is never merged, and embed each one in the PR description as `https://github.com/colinhallett/message-cp/blob/tessl/<issue id>-evidence/<file>.png?raw=true` (with `evidence/` before the file name if you keep them in that folder). The repository is private, so a `raw.githubusercontent.com` link shows a broken image to every reader; the `github.com/.../blob/...?raw=true` form shows the image to anyone who can see the repository. Never commit these evidence screenshots to the PR branch. An image the site itself serves, such as `site/public/dashboard-dark.png` and `site/public/dashboard-light.png`, is part of the change and is committed on the PR branch like any other file.
