# Caller identity

These rules extend the Design constraints in `AGENTS.md` for MCP tools in `src/server.ts` and the statements in `src/agents.ts`, `src/messages.ts` and `src/channels.ts` that read or change the caller's own state.

- A tool that acts as the caller passes the caller's registration down, from `session.requireAgent()` in `src/server.ts` (the caller's `Identity` from `src/agents.ts`, plus its name), not just the name from `session.require()`; `unregister` with no name, which passes `session.registration` as `own`, does the same. A statement that reads or changes the caller's own state finds its row by `id`, `registered_at` and `instance` (with `removed_at IS NULL`), never by name, inside the same transaction as the work it guards, because a removed agent's name can be registered again by another agent: `setStatus` in `src/agents.ts` updates that row and fails when none matches, `readInbox` in `src/messages.ts` finds it from the `Identity` the tools pass before marking anything read, and `checkLive` in `src/channels.ts` calls `nameOfIdentity` inside each channel tool's transaction. `sendMessage` in `src/messages.ts` uses its `own` parameter the same way, but only to clear the sender's status line. Matching by name stays right for the other party of a message or mention, for a person's send (`sendAsPerson` in `src/messages.ts`, from `POST /api/send`), for `touchAgent`'s last-seen bump, and wherever only a name is stored or served: `messages.sender` in `src/db.ts`, which is why `readConversation` matches the caller's sent messages by name and `created_at >= registered_at`, and the names in `/api/messages` and `/api/agents`. A finding that needs agent ids in a stored or served name changes a documented contract (and, for `messages.sender`, the database schema), so decline it with that reason, as the "Small, contained bounds" bullet in `AGENTS.md` says for such changes; for the other party, a person's send or `touchAgent`, decline it because the name is the key there.
