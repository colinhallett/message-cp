# Copy

These rules extend the Design constraints in `AGENTS.md` for `README.md`, `ops/*.md`, `site/src/pages/*.astro`, `site/public/llms.txt`, tool and parameter `description`s in `src/server.ts`, and `instructions()` in `src/wait.ts`.

- Text in `site/src/pages/*.astro`, `site/public/llms.txt`, `README.md` or a tool description in `src/server.ts` that tells someone to give an agent, or its wait command, a token names an agent token: one from `message-cp token add <account> --agent-only`, or the one `message-cp connect` prints. It never says "a full or agent token", because a full token also reads and deletes every conversation of the account (`GET /api/*`, `DELETE /api/conversation`) and, with `--public-url`, approves clients (`POST /oauth/approve`), which `src/http.ts` refuses an agent-only token; an operator's own check, such as the `npm run e2e` paragraph in `site/src/pages/server.astro`, may use a full token. Text that writes a token to a file shows the private write `server.astro` already uses: `mkdir -p ~/.message-cp && chmod 700 ~/.message-cp`, then `(umask 077 && printf '%s\n' '<token>' > ~/.message-cp/http-token)`. A client config that holds a token or agent key goes in the user's own file, such as `~/.cursor/mcp.json`, never in a project file that may be committed. The paragraph beginning "To add a client by hand instead" in `getting-started.astro` is the model to follow.
- Every sentence you add or change in `README.md`, or in a tool or parameter `description` in `src/server.ts`, states only what the code in the branch does after your diff. That covers claims about limits and cadences, accepted formats, which endpoint the dashboard calls, what a read-only token can see, and when the dashboard does something. Before opening the PR, list each such claim next to the line of code that makes it true, and cut or narrow any claim you cannot point to. Ask the fresh-eyes reviewer to make the same claim-by-claim check.
- The claim-by-claim check also covers, for each such sentence, the paths where the code does less than on its happy path: a database write that can fail or be skipped as busy, input another handler has already taken, an answer that arrives after the reader has moved on (a token change or a different view), and a read-only token. The sentence holds on each of those paths or states the exception. For example, `recordSession` in `src/http.ts` carries on when its `saveSession` or `touchSession` write fails or is skipped as busy, so a restart may lose a session it could not record; and `deletePair()` in `src/dashboard.ts` shows why the server refused a delete (400, 403 or 503) only while the same conversation is still open (`same`), so a reader who opened another one meanwhile sees no reason, while a 401 is handled before `same` and asks for another token in whatever view is open.
- The claim-by-claim check in the two bullets above, with its failure and edge paths, also covers every sentence you add or change in `site/src/pages/*.astro` and `site/public/llms.txt`. The wake-up instructions (what an agent does after its wait command or `wait_for_mail` returns) are written in nine places: `instructions()` in `src/wait.ts`, which every session is sent; the `register`, `read_inbox` and `wait_for_mail` descriptions in `src/server.ts`; "Waking on messages" in `site/src/pages/tools.astro`; "Waking remote agents" in `site/src/pages/server.astro`; "Woken when mail arrives" in `site/src/pages/index.astro`; the message-cp row's "How an agent learns of new messages" cell in `site/src/pages/compare.astro`; and `site/public/llms.txt`. A copy that tells an agent what to do after a wait returns says all of it: call `read_inbox` if the line names messages or mentions, and `read_channel` for each channel it names posts in; read before starting the command or calling `wait_for_mail` again; and, where it offers `wait_for_mail`, call it again when it returns `{ unread: null }`. Some copies say less today; a copy you change says all of it after your diff. When you change one copy, check the others in the same PR. `git grep -n -e 'start it again' -e 'starts it again' -e 'start the command again' -e 'starts the command again' -e 'wait again' -e 'unread&quot;: null' -e 'exits when it has' -e 'exits on mail' -- src site` finds each of them at the time of writing, but the list above is the authority: if a copy is reworded so the grep misses it, or a new copy is added, update the list and the grep. When you shorten or merge sentences, first list each condition the old text attached to a claim (who, when, on which process, after which answer, unless what). The new text keeps each one, or the PR description says, next to that condition, which linked page or section now states it, or which line of code shows it no longer holds. A claim that would be false without its condition keeps it even past a word cap: "ends when `DELETE` gets 200" does not become "ends on `DELETE`".
- Text in `README.md`, `ops/`, `site/src/pages/*.astro` or `site/public/llms.txt` that tells someone to run a `message-cp` command that opens the database (`account`, `token`, `connect`, `login-link`, `person`, `agent`, `webhook` or `wait`; `src/cli.ts` calls `openDb()` for each), or to copy, back up or restore the database file, says to do it where it reaches the same file `serve` uses. These commands open the file directly, not the server: a token made in another file is one the server refuses, and a person, agent or webhook added there is not the server's. `dbPath()` in `src/db.ts` is the raw `MESSAGE_CP_DB` (no `~` expansion, and a relative path is taken from the working directory), else `~/.message-cp/db.sqlite` under the `HOME` of whoever runs the command. So a command is run on the server, as the user `serve` runs as with that user's `HOME`, and with `MESSAGE_CP_DB` (if any) naming the same file, not a relative path from another directory; with Docker it is run inside the container with `docker compose exec message-cp message-cp ...`, because the `Dockerfile` sets `MESSAGE_CP_DB=/data/db.sqlite` there. Text that copies, backs up or restores the file names it explicitly: a shell snippet sets the database path in that snippet, as `DB="${MESSAGE_CP_DB:-$HOME/.message-cp/db.sqlite}"` in the "Database" section of `site/src/pages/tools.astro` does, or uses a `<database>` placeholder as step 4 of `ops/restore.md` does, and never hard-codes the database path; with Docker it names `/data/db.sqlite` on the compose volume `data`. The paragraph in `site/public/llms.txt` that begins "Over HTTP, to a running `message-cp serve`" is the wording to follow. Some copies say less today; a copy you change says all of it after your diff.
