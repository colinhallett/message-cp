# SQL

These rules extend the Design constraints in `AGENTS.md` for `SCHEMA` and `migrate` in `src/db.ts`, and the SQL prepared in `src/`: paged reads over a table that grows with history, and tables whose row ids the API, the dashboard or a tool hands out.

- A paged read you add or change (one with `LIMIT ? OFFSET ?`) over a table that grows with history (`messages`, `channel_posts`, `mentions`, `webhook_deliveries`) gets the same `EXPLAIN QUERY PLAN` check as SQL under the write lock (see the `.immediate()` bullet in `AGENTS.md`): run it against a database made by `openDb` before opening the PR, and put the plan lines in the PR description. The plan shows no `USE TEMP B-TREE FOR ORDER BY`, and every column the read filters or orders on, including inside a correlated `EXISTS`, is in the index the plan searches on that column's table, so a page reads about `limit + offset` rows rather than the whole history. If the plan falls short of that, add an index in `SCHEMA` in `src/db.ts`, as `messages_by_pair` and `webhook_deliveries_delivered_by_message` do, with a plan test modelled on "reads each direction through messages_by_pair in page order, without scanning or sorting history" in `test/conversation.test.ts`. That plan test explains the statement the production code prepares, as the `.immediate()` bullet in `AGENTS.md` says. Where the ticket prescribes a query that cannot avoid the sort or scan, the PR description says why it is bounded, with the plan lines. Paging stays `limit` plus `offset`: the index is what lets an offset page read only the rows it skips and returns, so do not switch to keyset or cursor paging to meet this. Paging over `agents` or `channels` (`listAgents` in `src/agents.ts`, the channel lists in `src/channels.ts`) is account-sized and is not covered, and a temp B-tree that sorts or groups only such a page after its `LIMIT` is bounded by `limit`; the history rows such a read counts or joins for its page are covered, so each joined history table is searched through an index on the join column, as `channel_posts_by_channel` is for the channel lists.
- A row id that the API, the dashboard or a tool hands out for a later request to act on (`DELETE /api/...?id=`, a confirmation the page keeps open) must never name a later row once its row is deleted, so its table is `INTEGER PRIMARY KEY AUTOINCREMENT`, as `messages`, `login_codes`, `dashboard_sessions` and `webhooks` are in `src/db.ts`. A table that databases made on main already hold is rebuilt keeping every row, its id and its indexes, as `rebuildLoginCodes()`, `rebuildDashboardSessions()` and `rebuildWebhooks()` in `src/db.ts` do, with a test modelled on theirs ("rebuilds a login_codes table from before AUTOINCREMENT, keeping every code, its id and its indexes" in `test/invites.test.ts` and "rebuilds a dashboard_sessions table from before AUTOINCREMENT, keeping every sign-in, its id and its index" in `test/signins-api.test.ts`). A table whose rows are only marked (`tokens.revoked_at`) needs none. Ids deleted before the rebuild cannot be recovered, and the PR says so.
