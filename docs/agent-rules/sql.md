# SQL

These rules extend the Design constraints in `AGENTS.md` for `SCHEMA` and `migrate` in `src/db.ts`, and the SQL prepared in `src/`: statements that hold SQLite's write lock (inside `.immediate()`, or a `DELETE` whose cascade reaches a child table), paged reads over a table that grows with history, and tables whose row ids the API, the dashboard or a tool hands out.

- SQL you add or change inside an `.immediate()` transaction, and a `DELETE` you add or change whose `ON DELETE CASCADE` or foreign key reaches a child table, holds SQLite's write lock while it runs. Check its plan with `EXPLAIN QUERY PLAN` against a database made by `openDb` before opening the PR, and put the plan lines in the PR description. Follow a cascade through every level: in `src/db.ts`, `webhook_deliveries.message_id` cascades from `messages` and is found through `webhook_deliveries_by_message`; `webhook_deliveries.post_id` cascades from `channel_posts` and still has no index, while `mentions.post_id` is found through `mentions_by_post`, so a change that first deletes from `channel_posts` adds that one index. A `SCAN` of a table that grows with history (`messages`, `channel_posts`, `mentions`, `webhook_deliveries`) gets an index in `SCHEMA` or `migrate` in `src/db.ts`, as `messages_by_sender` and `webhook_deliveries_by_message` do, with a plan test modelled on "finds the pair's messages and their webhook deliveries by index, without scanning other history" in `test/api-conversation.test.ts` or the `EXPLAIN QUERY PLAN` on `webhook_deliveries` in `test/webhooks.test.ts`; otherwise the PR says why the scan is bounded. A plan test explains the statement the production code prepares, not a copy typed into the test: it captures that statement with `vi.spyOn(db, "prepare")` while calling the function, as "reads the account's tokens through the agents primary key ..." in `test/api-approvals.test.ts` and "deletes its messages through messages_history and messages_by_sender ..." under "the plans of removing an agent" in `test/agents-api.test.ts` do, or it exports the SQL as a constant and explains that, as `TAKE_REPLY_SQL` in `src/messages.ts` and `COUNT_AGENT_TOKENS` in `src/login.ts` are. A literal stays right only for a statement SQLite runs itself, such as the child-table lookup an `ON DELETE CASCADE` makes (the `webhook_deliveries` line in the `test/api-conversation.test.ts` model). A statement that would bind one variable per row (an `IN (?, ?, ...)` built from a list) uses a subquery instead, as `purgeAgent` in `src/agents.ts` does with its `rows` subquery. A PRAGMA run under the write lock has no query plan to check, so it counts as a scan of what it reads: never run an unqualified `PRAGMA foreign_key_check` (or `integrity_check`) inside `.immediate()`, because it reads every table that has a foreign key, history included. A table rebuild shows that it copied every row the way `rebuildWebhooks()` in `src/db.ts` does, with a count query over the old and new tables (`COUNT_WEBHOOKS_COPIED`) and a plan test for that query ("checks the copy under the write lock by reading only the two webhooks tables, not other history" in `test/db.test.ts`). `addAccounts()` and `rebuildMessages()` still make the unqualified call; do not copy it from them.
- A paged read you add or change (one with `LIMIT ? OFFSET ?`) over a table that grows with history (`messages`, `channel_posts`, `mentions`, `webhook_deliveries`) gets the same `EXPLAIN QUERY PLAN` check as SQL under the write lock (see the `.immediate()` bullet above): run it against a database made by `openDb` before opening the PR, and put the plan lines in the PR description. The plan shows no `USE TEMP B-TREE FOR ORDER BY`, and every column the read filters or orders on, including inside a correlated `EXISTS`, is in the index the plan searches on that column's table, so a page reads about `limit + offset` rows rather than the whole history. If the plan falls short of that, add an index in `SCHEMA` in `src/db.ts`, as `messages_by_pair` and `webhook_deliveries_delivered_by_message` do, with a plan test modelled on "reads each direction through messages_by_pair in page order, without scanning or sorting history" in `test/conversation.test.ts`. That plan test explains the statement the production code prepares, as the `.immediate()` bullet above says. Where the ticket prescribes a query that cannot avoid the sort or scan, the PR description says why it is bounded, with the plan lines. Paging stays `limit` plus `offset`: the index is what lets an offset page read only the rows it skips and returns, so do not switch to keyset or cursor paging to meet this. Paging over `agents` or `channels` (`listAgents` in `src/agents.ts`, the channel lists in `src/channels.ts`) is account-sized and is not covered, and a temp B-tree that sorts or groups only such a page after its `LIMIT` is bounded by `limit`; the history rows such a read counts or joins for its page are covered, so each joined history table is searched through an index on the join column, as `channel_posts_by_channel` is for the channel lists.
- A row id that the API, the dashboard or a tool hands out for a later request to act on (`DELETE /api/...?id=`, a confirmation the page keeps open) must never name a later row once its row is deleted, so its table is `INTEGER PRIMARY KEY AUTOINCREMENT`, as `messages`, `login_codes`, `dashboard_sessions` and `webhooks` are in `src/db.ts`. A table that databases made on main already hold is rebuilt keeping every row, its id and its indexes, as `rebuildLoginCodes()`, `rebuildDashboardSessions()` and `rebuildWebhooks()` in `src/db.ts` do, with a test modelled on theirs ("rebuilds a login_codes table from before AUTOINCREMENT, keeping every code, its id and its indexes" in `test/invites.test.ts` and "rebuilds a dashboard_sessions table from before AUTOINCREMENT, keeping every sign-in, its id and its index" in `test/signins-api.test.ts`). A table whose rows are only marked (`tokens.revoked_at`) needs none. Ids deleted before the rebuild cannot be recovered, and the PR says so.
