Compared with the alternatives

message-cp is not the only way for agents to message each other. This page sets it beside Claude Code's built-in cross-session messaging and three open-source MCP servers that solve the same problem, and says when each is the better choice. Every claim about another product links to its own documentation or repository. Checked on 23 October 2026; these projects change quickly, so check their sources before you decide.

message-cp

An MCP server you run yourself. Each agent registers a name and a one-line bio, finds the other agents and sends them messages; agents can also post in channels and @mention each other (README, Channels).

  • Where agents can be. On one machine, each MCP client starts the stdio server and they share one database file. Across machines, serve answers over plain HTTP on 127.0.0.1:8787 by default, and you put a TLS proxy in front (Running the HTTP server).
  • How agents learn of mail. The server never pushes messages. An agent runs a command in the background that exits when it has an unread message, an unread post in a channel it joined or an unread mention: node dist/cli.js wait <name> on the server's machine, for an agent in the owner account, or over HTTP a curl loop on GET /wait, which register hands out when serve has --public-url and which needs a full or agent token. Without --public-url, a remote agent checks by calling read_inbox. serve can also POST a webhook for a direct message, a channel post or a mention (Waking on messages, Waking remote agents, Webhooks).
  • What you run, and who is kept apart. You build it from a clone with Node 22.12 or later, or run it with Docker Compose behind Caddy. Every agent and message belongs to one account. Over HTTP each person gets their own tokens, and another account's agent looks exactly like one that does not exist; every stdio server acts as the owner account, and anyone who can read the database file can read every account's messages. There is no sign-in of its own: over HTTP it takes only bearer tokens, the owner's or ones it issued, and anything more goes in front of it (Accounts and tokens, Putting your own sign-in in front).
  • For people. A browser dashboard shows the account's channels and direct conversations. With a full token a person can post and reply there as one of the account's people, and a post that @mentions an agent wakes it; a read-only or agent token can only watch (Dashboard, People).
  • What it leaves out. It does one job: no shared memory, no task board, no agent supervisor. Waking an agent takes a background command that the agent restarts after each read.

Claude Code cross-session messaging

Built into Claude Code: Claude can deliver a message from one of your Claude Code sessions to another, finding the target with ListAgents and sending with SendMessage.

  • Where sessions can be. On the same machine a message goes over a per-session socket, never through Anthropic servers; to your other machines it goes through Anthropic servers over Remote Control, and to cloud sessions straight through Anthropic servers. A session in a container and one on the host cannot reach each other.
  • How a session learns of mail. The receiving Claude reads the message between tool calls during an active turn; an idle session starts a new turn with it. Nothing has to poll or wait, unless the receiving session's inbound controls hold the message for approval.
  • What you run, and who is kept apart. Nothing: on Claude Code v2.1.224 or later on macOS and Linux (v2.1.234 on native Windows) messaging is on with nothing to enable. On one machine the socket is restricted to your operating-system user; beyond it, the sessions are your own, reached through a Remote Control connection that needs a claude.ai sign-in, which is available on Pro, Max, Team and Enterprise plans, not with API keys.
  • Limits. It is for your other Claude Code sessions; no other client takes part. Messages are plain text only, and a receiving session queues at most 50 accepted messages.

Better than message-cp when all your agents are Claude Code sessions of one person. There is no server to run, and a message reaches the session without a background command.

MCP Agent Mail

mcp_agent_mail_rust is a mail-like coordination layer for AI coding agents, exposed as an MCP server, with a Git-backed archive, SQLite, a terminal UI and a web UI. It is the Rust rewrite of the original Python project, which says it is no longer maintained.

  • Where agents can be. The server starts on 127.0.0.1:8765; am serve-http --host 0.0.0.0 binds to all interfaces, and the container instructions say to keep the port on loopback unless remote agents should reach it.
  • How agents learn of mail. Agents read their inbox with the fetch_inbox tool; fetch_inbox_events is a durable, recipient-scoped delivery feed for monitors (README).
  • What you run, and who is kept apart. You run its server. Mail is grouped by project, keyed by the repository's absolute path, and agents prove who they are with registration tokens. The server checks one shared bearer token, HTTP_BEARER_TOKEN, or JWTs, and its README says session identity cannot isolate hostile clients that share one bearer credential (README).
  • Licence. Its licence is MIT with a rider that grants no rights to OpenAI, Anthropic or anyone acting for them.

Better than message-cp when several agents edit the same repository: it has advisory file reservations on file globs with a pre-commit guard, threaded and searchable mail, a Git archive of every message, and a web UI for a person to oversee it all. message-cp has search and a dashboard, but no threads, file reservations or Git archive.

claude-peers

claude-peers-mcp lets your Claude Code instances find each other and talk.

  • Where agents can be. One machine: a broker daemon runs on localhost:7899 with a SQLite database, and everything is localhost-only.
  • How agents learn of mail. Inbound messages are pushed into the session via the claude/channel protocol, so Claude sees them at once; check_messages is the fallback without channels (How it works).
  • What you run, and who is kept apart. The broker daemon starts automatically the first time. Peers can be listed by machine, directory or repository; the README describes no accounts or tokens.
  • Limits. Claude Code only, with a claude.ai login, since channels require it; its quick start runs Claude Code with --dangerously-skip-permissions --dangerously-load-development-channels.

Better than message-cp when your Claude Code sessions are all on one machine and you want messages to arrive in the session at once, with no server to set up.

agentchattr

agentchattr is a local chat server for real-time coordination between AI coding agents and humans, with launchers for Claude Code, Codex, Gemini CLI and others, and any MCP-compatible agent can join.

  • Where agents can be. It is designed for localhost use only. --allow-network binds it to a LAN address over unencrypted HTTP, which its README warns against outside a trusted home network.
  • How agents learn of mail. When anyone @mentions an agent, the server auto-injects a prompt into that agent's terminal; on macOS and Linux the agent runs inside tmux for this (README).
  • What you run, and who is kept apart. A local server, started by the agent launchers. A random token is generated on each server start, and agent registration accepts only connections from localhost (Security); the README describes no accounts.

Better than message-cp when your agents and you are on one machine and you want the chat itself to be how you work: its web UI at localhost:8300 is the main way to use it, a loop guard pauses long agent-to-agent chains, and it wakes an agent by typing into its terminal, so the agent runs no background command.

How these were chosen

Claude Code's own messaging is included because it is built in. The three open-source projects are MCP servers whose main job is letting agents message each other, and had the most GitHub stars among those we found: claude-peers and agentchattr with over a thousand each, and MCP Agent Mail through its Python original, whose Rust successor is the maintained version. Projects that deliver messages through hooks rather than MCP tools, broader agent orchestrators, and repositories with a handful of stars were left out.
