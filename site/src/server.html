Running the HTTP server

export MESSAGE_CP_HTTP_TOKEN="$(openssl rand -hex 32)"
node dist/cli.js serve --port 8787 --public-url https://message-cp.example.com

Keep the token: you need it for clients, the wake-up loop and npm run e2e. To try serve on one machine without a domain, leave out --public-url and use http://127.0.0.1:8787 wherever this reference shows https://message-cp.example.com.

serve [--host <address>] [--port <port>] [--public-url <url>] (see Settings for each flag's default) serves the same tools over MCP's streamable HTTP transport at /mcp, against the same database as the stdio server. Both can run at once on the same file, and agents on either see each other.

  • Token. serve refuses to start unless MESSAGE_CP_HTTP_TOKEN is set and non-empty. Every request but GET / (the dashboard page, which holds no data) and requests to /health (the health check, see Settings, which answers every request the same with or without a token) must send Authorization: Bearer <token>, with that token or one made with node dist/cli.js account add or token add (see Accounts and tokens). Anything else, a revoked token included, gets 401 and touches nothing. MESSAGE_CP_HTTP_TOKEN is the owner account's token. It lives only in serve's environment, not in the database, so account list shows the owner with tokens: none; change it by restarting serve with a new value.

  • Address. It listens on 127.0.0.1:8787 unless --host and --port say otherwise (see Settings), and speaks plain HTTP. Exposed without HTTPS, the token and every message cross the network in the clear. Put a reverse proxy that terminates TLS in front and expose only that. With Caddy, which gets the certificate itself, this Caddyfile is enough:

    message-cp.example.com {
	reverse_proxy 127.0.0.1:8787
}

    Run it with caddy run --config Caddyfile. Any proxy works as long as it passes the Authorization header through unchanged and does not cut off a request held for about four minutes (/wait, below).

  • Public URL. --public-url is the HTTPS address clients use, without /mcp. With it, the server tells each session how to be woken over HTTP (below); without it, remote agents check for mail by calling read_inbox.

  • Sessions. Each MCP session is one agent once it calls register, or from its start if the initialize request that opened it sent X-Message-CP-Agent: <name> and X-Message-CP-Agent-Key: <key>. A session belongs to the account whose token started it; a request on it with another account's token gets 404, as if it did not exist. A session ends when the client sends DELETE or after 30 minutes idle. A GET /wait held on the same server for the agent the session is registered as, with a token of the session's account, counts as use while it is held and as it ends, so a session whose agent keeps waiting is not dropped. It also stays restorable if serve could record that use in the database (a database too busy means it was not, until a later hold records it). The server keeps at most 256 sessions and answers 503 beyond that. A session that has called register survives a restart of serve if serve could record its latest register in the database (a database too busy, say, means it was not recorded, and that is not retried): its next request with the same Mcp-Session-Id and a token of the same account acts as the same agent, with no new register, and counts against the 256 like a new session. A DELETE that cannot be recorded in the database gets 500, and the session can then be restored and the DELETE sent again; after one that gets 200, any server sharing the database answers the session's next request with 404. It is not restored if it was ended with DELETE, has been idle past the timeout, or its agent has been removed since (by unregister or message-cp agent remove) or given a new key (by message-cp agent key reset); that request gets 404 Unknown session, as does a session that never registered. A request that was in flight while the server stopped is lost, and the client sees its connection drop.

  • Agent headers. An initialize request without an Mcp-Session-Id that sends both X-Message-CP-Agent and X-Message-CP-Agent-Key registers that agent in the token's account as register with that name and key (and no bio, so an existing agent keeps its bio) would, and the new session starts as that agent. It is recorded for restarts as a session that called register is, with the same exceptions (a write that is busy or fails is not retried), so its next request with the same Mcp-Session-Id is restored as above. A client that instead opens a new session with the same headers after a restart, a dropped connection or a long sleep is the same agent, with the same messages, unless the agent has been removed meanwhile, when the headers register a new agent with that name, or its key has been reset with message-cp agent key reset, when they are refused with 403 until they carry the new key. The headers are read only on a request without an Mcp-Session-Id: a request on an existing session, a restored one included, ignores them, and register and unregister work on any session as before. A refusal creates no session: a wrong key for an agent that has one, a person's name, an invalid name or an invalid key gets 403 with the message register would give; a database too busy gets 503 with Retry-After; and a request without an Mcp-Session-Id that sends only one of the headers, or either more than once, gets 400 before the 256-session cap is checked. Neither header's value is logged.

  • Logging. serve prints one line to stderr when it starts listening, and one line for an internal error. It does not log requests, tokens or message bodies.

Dashboard

Open the server's address in a browser, for example https://message-cp.example.com/ or http://127.0.0.1:8787/, and paste a token for your account. A read-only token (node dist/cli.js token add <account> --read-only) is enough to watch; a full token can also post and reply as one of the account's people (see below). An agent token (--agent-only) sees the page as a read-only token does. The page is laid out like a chat app. The left sidebar lists the account's channels (each one's tooltip gives its post count, its members and when it was last posted to, or that it has no posts) and the pairs of agents that have messaged each other (each one's tooltip gives how many messages they have exchanged). Each channel and pair shows an unread badge: how many posts or messages arrived since this tab last had it open. What is there when the page first loads counts as seen, so a fresh load shows no badges; a channel or pair that appears later starts with everything in it unread. The badges are kept only in the tab's memory, so a reload or a new token starts again, and they mark nothing read for any agent. The open conversation is highlighted with an accent bar and shows no badge, since what arrives in it is seen at once. Choose one to read it in the middle as a chat log, under a header bar that names it and holds the Close button; for a channel the bar also lists, under its name, the agents who have joined it (or says No members yet), following each refresh, with a long list cut short and given in full on hover. For a direct conversation the bar shows, under its names, the status line of each agent in it that has one, as <name>: <status> (two joined with ·), cut short when long and given in full on hover; it comes from the last GET /api/agents answer the page read, so it shows as soon as the conversation opens, follows each refresh that reads both GET /api/agents and GET /api/channels (one where either fails or answers 503 leaves it as it was; a refused token, 401, clears the page and asks for another, as anywhere else on it), and so goes on such a refresh once the line clears or expires or the agent is no longer listed. It works with a read-only token, and a person never has one. The log is oldest first and newest at the bottom, each entry with its sender, time and text. A log with only a few entries sits at the bottom of the middle area, as in a chat app, just above the compose box when there is one. Each @name in an entry's text is highlighted, found as the server finds mentions (a@bob is not one), @all included; with a full token and a person chosen in the "Post as" picker (see below), a mention of that person stands out more, and changing the person re-marks the open log at once. Each http:// or https:// address in an entry's text, in the log and in search results, is a link that opens in a new tab without telling the site which page it came from; punctuation at its end (such as ., ,, ) or ") is left out, except a ) that closes a ( in the address, and an @name inside an address shows as part of the link, not highlighted (the server still records it as a mention). Nothing else is a link: not javascript:, data:, mailto: or ftp://, and not an address without its scheme, such as www.example.com. An entry sent less than 5 minutes after the entry just before it, by the same sender, sits under that entry's name with no name or avatar of its own; a broadcast always starts its own entry, so its mark shows. Each group starts with an initials avatar in a colour that is always the same for that name: round with a "person" label for a sender the right panel lists as a person, and square for anyone else, which follows the panel as it refreshes. Times read as "just now" within a minute either way, as "2m ago" or "3h ago" within the last 12 hours, and otherwise as the time today or the date and time before, with the full date and time on hover. A broadcast is marked as one and appears in the conversation of each recipient, and a message to an agent that has since unregistered stays, under the name it was sent to. In a direct conversation, each message to an agent shows a receipt after its time: "read" once its recipient has picked it up with read_inbox, "starting…" before that once GET /api/messages gives it starting: true (a webhook on that agent has delivered it: its receiver answered 2xx), and "not read yet" before either (for a broadcast, whether that conversation's recipient has read their copy). After reading the new messages, each refresh asks GET /api/messages?unread=true for every unread message to an agent in the account, and a message the page showed as "not read yet" before that refresh, to a name that refresh lists as an agent, turns to "read" in place, without a reload, once it is no longer among them, and one still among them with starting: true turns to "starting…" the same way; a receipt only moves from "not read yet" to "starting…" to "read", never back, so "starting…" stays even if the webhook is removed before the agent reads the message. So a message is first checked on the refresh after the one that brought it in, though one that GET /api/messages already gives starting: true shows "starting…" from the start. A message read while those pages are being read can make the next one be missed, so that one keeps its receipt until a later refresh; and when that read fails or the server is busy (503), no receipt changes until a refresh succeeds. A message deleted elsewhere while the page shows it (from another tab, or with agent remove or person remove) also turns to "read" once its recipient's name is an agent's, and one to an agent that has since unregistered or been removed keeps the receipt it had when its name stopped being an agent's (or, when the page first loaded it after that, the one it first showed: "starting…" if a webhook had delivered it), and a later delivery does not change it. While no message the page holds to an agent is unread, the refresh does not ask. A message to a person (a name the right panel lists as a person) shows no receipt, since a person has no read_inbox, and nor do search results. In an open channel, a post that mentions an agent of the account shows a receipt after its time with one part per agent it gave a mention (none for its own sender), in name order, for example "bob: read · carol: not read yet": "read" once that agent has picked the mention up with read_inbox, and "not read yet" before. A mentioned person is left out, so a post that mentions only people, or no one, shows no receipt, and a mentioned agent that has since unregistered shows the name it had. While a post the log holds still has a mention shown as "not read yet", each refresh that reads the channel's new posts without a failure then asks GET /api/channel-posts?channel=<name>&unread=true for every post in the channel with an unread mention of an agent, and a part turns to "read" in place, without a reload, once its post is no longer among them or that answer gives that name as read; a part never turns back. A mention deleted while the page shows it (with agent remove or person remove) also turns to "read" once its post has no unread mention left. As with messages, a mention read while those pages are being read can make the post after a page boundary be missed, so it keeps its receipt until a later refresh; and when that read fails, the server is busy (503), the channel is gone (404), or the answer comes after another conversation opened or the token changed, no receipt changes. The receipts read the same way with a read-only token, and mark nothing read. The right panel lists the account's agents and people, one compact line each: its mark (an online or offline dot for an agent, a "person" label for a person), its name (a long one cut short), its status line when GET /api/agents gives one (see set_status; also cut short when long) and one unread badge, the sum of its own unread messages, posts and mentions, hidden at 0. A status line that has cleared or expired goes on the next refresh that succeeds. The full status line, its bio, when it was last seen (for a person, when they were added) and the three separate counts show on hover, and in a details part that clicking or tapping the row, or Enter or Space on it, shows and hides; a row left open stays open as the panel refreshes. The badge is the agent's own unread mail, not what this tab has seen, and opening a row's details sends nothing and marks nothing read. Everything refreshes every few seconds, and new posts and messages appear in the open conversation without a reload. The search box in the top bar asks GET /api/search for the newest 200 direct messages and channel posts in the account whose text contains what you typed, and shows them in the middle in place of the open conversation, newest first: each with its sender, time and text, a post with its #channel, and a message with its recipient (→ name) and whether it was a broadcast, with mentions highlighted as in the log. It says when nothing was found or when only the newest 200 are shown. The results are not refreshed with the rest; search again to refresh them, or choose a conversation or click Close to leave them. The sidebar's "Webhook deliveries" entry, under "Webhooks", shows the account's newest 200 webhook deliveries in the middle the same way, newest first: each with its --on (such as #general, mention:alice or agent:bob), its webhook id, when it was queued, its attempts, its status (delivered, pending, or failed, which is marked in red) and, once delivered, when. Its count is how many it read when last open, and it says when there are none or when only the newest 200 are shown. Unlike the search results it refreshes with the rest while it is open. A failure to read the deliveries is shown in that view and does not stop the rest of the page refreshing, except that a token the server refuses (401) clears the page and asks for another, as anywhere else on it. It never shows a webhook's URL or secret, or a message's text, and it cannot add, remove or retry a webhook or a delivery. An empty sidebar, agents panel or webhook deliveries view says how to fill it: which tool or command makes something appear there and, with a full token, that "New channel" or "New message" starts one. The page follows the browser's light or dark setting, and on a screen up to 720px wide the header bar, the open conversation and the compose box fill the screen while neither panel is open, and the ☰ and Agents buttons slide the sidebar in from the left or the agents in from the right, over the conversation (without the slide when the system asks for reduced motion). The open panel closes when its button is pressed again, when the other button opens the other panel, on Escape (an Escape in an open New message or New channel form, or in the mention list, closes that first, and one while a delete confirmation is showing dismisses it instead), on a tap on the part of the conversation it leaves uncovered (focus left in the panel goes back to its button), or when a conversation, the webhook deliveries or search results open.

The token stays in that browser tab's sessionStorage until you click "Forget token", the server refuses it, or the tab closes. It never goes into a cookie or a URL. The page reads through GET /api/agents, GET /api/channels, GET /api/channel-posts, GET /api/messages, GET /api/search and GET /api/webhook-deliveries, and reading a channel or the messages there marks nothing read for any agent. It asks GET /api/token once whether the token is read-only or agent-only.

With a read-only or agent token, or when that answer cannot be read, the page shows no way to post: it cannot register, send, post or change anything. With a full token, a "Post as" picker under an open channel or direct conversation, beside the compose box at the bottom of the log, lists the account's people (or names message-cp person add when there are none), and the person chosen there lasts while the tab is open, or until they are no longer in GET /api/agents. With a person chosen, a compose box under an open channel posts in it as that person through POST /api/post, and one under an open direct conversation the person is one side of replies to the other side through POST /api/send; a conversation between two others has none. To write first to an agent or person, choose "New message" beside the "Direct messages" heading (it shows only with a full token): pick who you are under "From", from the account's people (it starts at the "Post as" person, if one is chosen, and otherwise asks for a choice, and names message-cp person add when there are none), and who to write to under "To", from the account's agents and people in the right panel, each person marked as one, without all or yourself. If the name chosen in either goes from the list while the form is open, that select goes back to asking for a choice rather than picking another name, and "Open" opens nothing until one is made. "Open" chooses you in "Post as" and opens the conversation of the two of you as if you had chosen it in the sidebar, with the compose box under it; one with no messages yet is listed first in the sidebar, with no badge, whatever arrives in other conversations, and says "No messages yet." until the first is sent, and is forgotten with the token. Escape or Cancel closes the form, as does opening another conversation. To create a channel, choose "New channel" beside the "Channels" heading (it too shows only with a full token): pick who you are under "From" (it starts at the "Post as" person, and names message-cp person add when there are none), give the channel a "Name" of 1-32 letters, digits, - and _, and write its "First post", since a channel is created by its first post. A name the sidebar already lists, in any case, is refused with a note rather than posted in, as are a blank post and one longer than 4000 characters; nothing is sent until all of these pass. "Create" posts the first post through POST /api/post, chooses you in "Post as" and opens the new channel with the compose box under it. A refusal keeps the text with the reason in the form. With no answer it keeps the text and says to check the channel list, and since the post may still be stored, the page refuses that name until the token is forgotten. That guards only this page: after the token is forgotten, in another tab, or when someone else creates the same name first, "Create" posts in the channel that exists, because POST /api/post creates a channel or adds to it. Only one of "New message" and "New channel" is open at a time, and Escape, Cancel or opening another conversation closes either. Enter sends and Shift+Enter adds a line (an Enter that ends an input method's composition does neither, and one in an empty box sends nothing), and the Send button still sends for anyone who does not use Enter. Typing @ at the start of the text or after any character but an ASCII letter or digit, _ or - (so a@b offers nothing, but é@b does) opens a list of the account's agents and people from the right panel, each person marked as one, without the person you post as or all; the letters typed after the @ narrow it to names that start with them, ignoring case, and it shows at most 8. When no such name starts with what was typed (@zz, or @all), no list opens, and an open one closes. ArrowDown and ArrowUp move the highlight, Enter or Tab picks the highlighted name and a click picks any, each putting @<name> in place of what was typed; Escape closes the list and keeps the text, so the next Enter sends. While the list is closed, Enter, Shift+Enter and Tab do what they always do. The box starts at 2 lines and grows with its text up to 10, then scrolls, and goes back to 2 lines when a send clears its text (see below for when it does). What is sent is stored and delivered as an agent's would be, so an @<agent> in a post wakes that agent and webhooks fire, and it appears in the open conversation at once. The box takes at most 4000 characters, counted as the server counts them (an emoji is one). A refusal is shown under it with the text kept (a 400 with the server's reason); the text is cleared only once the server has taken it, and an answer only changes the box while it still sends to the same conversation as the same person. Send stays disabled while a send is in flight. When it gets no answer (the connection fails, or 15 seconds pass), it may still have been stored, so the text is kept with a note to check the conversation before sending it again; the page does not try to find out itself, so sending it again can store it twice. A token the server refuses (401) clears the page as anywhere else on it. To delete a direct conversation, open it with a full token: while it has at least one message, its header bar has a "Delete" button beside Close (never for a channel, the webhook deliveries, search results or a conversation from "New message" with no messages yet). "Delete" sends nothing yet: it asks in the header bar, naming both sides and how many of their messages the page holds ("Delete the 12 messages between alice and bob? This cannot be undone."), with "Delete" and "Cancel". Since the server matches names ignoring the case of A-Z, a pair the sidebar lists apart only by that case (Bob and bob with alice) is deleted with it, so the confirmation names and counts those pairs too. The count is what the page holds: the server deletes every message between the two names when the request arrives, including one the page has not read yet. Cancel, Escape, opening another conversation, Close and forgetting the token dismiss it without sending anything. Confirming sends DELETE /api/conversation with the two names, and the confirming Delete stays disabled while it is in flight. Once the server has deleted them, the page closes the conversation if it is still open, forgets what the tab had seen of it and of the pairs deleted with it, and reads every direct message again, so the sidebar lists the pairs that still have messages, and the conversations from "New message" that have none yet. A refusal that comes while the conversation is still open keeps it open with the reason in its header bar; one that comes after another conversation opened shows nothing. With no answer (the connection fails, or 15 seconds pass) the messages may already be deleted, so the page reads them all again, and says so in the header bar if the conversation is still open. A token the server refuses (401) clears the page as anywhere else on it. Posting, sending, creating a channel by its first post and deleting a direct conversation are all the page ever writes. GET / and requests to /health (see Settings) are the only requests answered without a token: GET / gives the same page with no data to everyone, and /health the same answer to everyone. The page loads nothing from other origins and cannot be framed.

Waking remote agents

A remote agent needs only sh and curl. Tell it "register as alice and turn on push". With --public-url set, register returns waitCommand: a curl loop that asks GET /wait?agent=alice until mail arrives, prints one line such as 1 unread message from bob, and exits 0. The agent runs it as a background command (in Claude Code, a Bash call with run_in_background), calls read_inbox when it fires (and read_channel for each channel the line names, if it has joined channels), and only then starts it again; started before reading, it fires at once on the same message.

The loop reads the token from MESSAGE_CP_HTTP_TOKEN, else from ~/.message-cp/http-token on the agent's machine. Put the token there once:

mkdir -p ~/.message-cp && chmod 700 ~/.message-cp
(umask 077 && printf '%s\n' '<token>' > ~/.message-cp/http-token)

The loop hands the token to curl on stdin, so it never appears in the agent's instructions, a tool result or the process list. A 401 or 404 ends the loop with an error, since asking again cannot help.

Checking a server end to end

npm run e2e

starts dist/cli.js serve on a free port with a temporary database and a generated token, and checks it the way remote agents use it: no token or a wrong token gets 401; two clients register; /wait reports no mail, then answers soon after one agent messages the other; read_inbox returns the message; both agents unregister. When it finishes, even after a failure, it tries to delete every direct message to or from either agent, for at most 60 seconds; if it cannot, it says so and exits 1. It prints one line per step and exits 0, or names the failed step and exits 1.

To check a running server instead, give it the URL and a full or agent (not read-only) token for any account:

MESSAGE_CP_HTTP_TOKEN=<token> npm run e2e -- --url https://message-cp.example.com

The URL must be https (plain http only for 127.x.x.x or [::1]). It registers agents named e2e-<random>-a and -b in that token's account; before it exits, even after a failure, it tries to unregister them and delete every direct message to or from either name, and exits 1 if it cannot. It never prints the token.

Running with Docker

The repository has a Dockerfile, which builds message-cp from the clone and runs node dist/cli.js serve on port 8787 of the container, and a docker-compose.yml, which runs it behind Caddy for HTTPS. Nothing is published to a registry, so the image is always built from your clone. You need Docker with Compose, and a domain whose DNS points at the machine with ports 80 and 443 reachable, so that Caddy can get its certificate (see Address under Running the HTTP server).

git clone https://github.com/colinhallett/message-cp.git
cd message-cp
cp .env.example .env    # then set MESSAGE_CP_DOMAIN and MESSAGE_CP_HTTP_TOKEN in it
docker compose up -d
  • Settings. (Every setting, Docker's values included, is listed under Settings.) MESSAGE_CP_DOMAIN is the public domain, for example message-cp.example.com. It is the only place the domain is set: Caddy serves that site address (from the committed Caddyfile), and serve gets --public-url https://<domain>. MESSAGE_CP_HTTP_TOKEN is the owner account's token (for example from openssl rand -hex 32), read when the container starts and kept out of the image. Compose reads both from .env or from the environment, and a value set in the shell's environment wins over the one in .env. If either is missing or empty, docker compose up stops before starting anything and names it. .env is ignored by git and left out of the image build. After changing either, run docker compose up -d again to restart with the new value.
  • Network. Only Caddy publishes ports: 80 and 443 (443 over TCP, and over UDP for HTTP/3). message-cp is reachable only on the compose network, at message-cp:8787, where Caddy forwards to it, so its plain HTTP never leaves the machine. Clients, the dashboard and the wake-up loop use https://<domain> as anywhere else in this reference.
  • Data. The database is /data/db.sqlite in the container, on the named volume data, and Caddy's certificates are on the volume caddy_data. Both survive docker compose down followed by docker compose up -d; docker compose down -v deletes them. message-cp runs as the image's non-root node user, which owns /data.
  • Server commands. Run them in the running container, against the same database: for example docker compose exec message-cp node dist/cli.js account add alice or docker compose exec message-cp node dist/cli.js account list. Every command under Accounts and tokens for a team works this way, and docker compose exec message-cp node dist/cli.js connect <agent> --url https://<domain> prints a ready client setup for an agent (see Agents).
  • Updating. After git pull, run docker compose up -d --build to rebuild the image and restart with it; the volumes are kept.

To try it on one machine without a domain, set MESSAGE_CP_DOMAIN=localhost: Caddy then serves https://localhost with a certificate from its own local authority, which clients, including the wake-up loop's curl, do not trust unless you add that authority.

Settings

Every setting the stdio server, serve, the node dist/cli.js commands, npm run e2e and the /wait loop read, in one place. Besides these they read no MESSAGE_CP_ variable and no config file. The deployment and backup scripts in ops/ have settings of their own (such as MESSAGE_CP_BACKUP_URL_FILE for ops/backup.sh, and /etc/message-cp.env, which ops/message-cp.service loads to run serve), described in ops/README.md, ops/deploy.md and the scripts themselves.

Setting Default What reads it
MESSAGE_CP_HTTP_TOKEN none serve, which refuses to start when it is unset or empty; the owner account's token (see Token under Running the HTTP server). Also npm run e2e -- --url (the token it checks the server with; without --url it makes its own), and the /wait loop, which treats an empty value as unset.
MESSAGE_CP_DB ~/.message-cp/db.sqlite Every process that opens the database: the stdio server, serve and every node dist/cli.js command (dbPath in src/db.ts). An empty value means the default.
MESSAGE_CP_AGENT, MESSAGE_CP_AGENT_KEY none The stdio server only, both or neither: it starts registered as that agent of the owner account (registerFromEnv in src/agents.ts; see Names, keys and identity). Only one set, or either empty, and it prints an error and exits.
~/.message-cp/http-token read if present The /wait loop, on the agent's machine, when MESSAGE_CP_HTTP_TOKEN is unset or empty (CURL_LOOP in src/wait.ts).
serve --host <address> 127.0.0.1 serve: the address it listens on (see Address under Running the HTTP server).
serve --port <port> 8787 serve: the port it listens on, 0 to 65535.
serve --public-url <url> none serve: the http:// or https:// address clients use, without /mcp, so it can tell sessions how to be woken over HTTP (see Public URL under Running the HTTP server).

A flag serve does not know, one given twice, or a bad --port or --public-url prints serve's usage line and exits 2.

With Docker, the Dockerfile sets MESSAGE_CP_DB=/data/db.sqlite and runs serve --host 0.0.0.0 --port 8787, and docker-compose.yml runs the same serve with --public-url https://<MESSAGE_CP_DOMAIN> added and passes MESSAGE_CP_HTTP_TOKEN in. MESSAGE_CP_DOMAIN (no default; docker compose up refuses to start without it) is read by docker-compose.yml and the Caddyfile, not by message-cp. Compose reads MESSAGE_CP_DOMAIN and MESSAGE_CP_HTTP_TOKEN from .env (see .env.example) or the environment.

Health check. /health answers without looking at the token, so every caller gets the same answer whether it sends a valid token, a wrong one or none: GET gets 200 with {"ok":true}, and any other method 405 with Allow: GET.
