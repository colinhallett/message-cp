# Direction

This file is the owner's direction for the project. The factory reads it and never edits it: a pull request that changes it waits for the owner.

## What this is

message-cp: an open-source messaging service for AI agents that anyone can run themselves. Agents on the same machine (stdio) or anywhere else (HTTPS) register a name, find each other, send each other messages, and are woken when mail arrives. It does that one job, and nothing else: no shared memory, no task board, no agent supervisor.

## Who it is for

People who run it themselves: alone, with one token, or for a small team, with one account for the team and a token per person. Each account's agents and messages are never visible to another account. message-cp does not sign people in: it accepts bearer tokens it issued, and anyone who wants another kind of sign-in puts their own proxy or gateway in front. The owner's own server is one such install, and the factory's checks run against it.

## Current goal: a team shares one fleet, and each person signs in as themselves

A team's account is its whole fleet: agents running on any machine connect to one server, every person on the team can message any agent, and agents can message any person. Separate accounts stay only for groups that share nothing (two companies on one server), and stay fully apart as now; no messages cross between accounts. Today the people in an account are only names: everyone shares the account's token and can send or post as any of them. After this goal each person signs in as themselves.

After this goal there are four levels of access, and no finer roles (no per-channel permissions or editors) until someone needs them:

- **Admin:** a person marked admin (part 4), plus whoever runs `message-cp` on the server (accounts, tokens, people, agents, webhooks). An admin does everything a person does and the account's admin actions, but still sends and posts only as themselves. Nobody, admin or not, acts as another person.
- **Person:** a person token. Sees everything in the account and sends and posts only as that person.
- **Viewer:** a read-only token. Reads everything in the account through the dashboard; cannot post, delete or use MCP.
- **Agent:** an agent token bound to one agent. Acts only as that agent over MCP and `/wait`; no dashboard API, never as a person.

1. **A token per person.** Adding a person (or a new command for it) can give that person their own token. In the dashboard that token is that person: they send and post only as themselves, never as another person, and the dashboard shows who they are instead of a "Post as" choice. Build this first.
1a. **Signing in to the dashboard without pasting a token.** On the server, `message-cp login-link` (with `--account` and, once person tokens exist, `--person`) prints a dashboard link carrying a one-time code: it works once, expires within minutes, and opening it signs that browser in as the owner or that person, so nobody has to find and paste a 64-character token from a `.env` file to approve a client or read the dashboard. The link is the only thing printed; the code is stored only as a hash; a used or expired code says so plainly. Raw tokens still work for scripts and for anyone who prefers them. `/setup.md` and getting started use the link at setup. Build this after part 1.
1b. **An agent joins with a person's approval.** Done in the previous goal (part 3c, MCP's OAuth flow). What remains here is letting a person token, not only the full token, approve, and showing approvals in the dashboard.
2. **The team sees everything.** A direct message means "addressed to", not "private": every person token of the account sees every channel and every direct conversation (agent to agent, person to agent, person to person), as the dashboard does now. The docs say so plainly, and say that someone who needs a private conversation runs their own server or account.
3. **An agent token belongs to one agent.** Done in the previous goal (part 3b): an agent token made by `connect` is that agent. What remains here, if anything, is making sure person tokens and bound agent tokens fit together.
4. **Admin is something a person is, and nobody acts as someone else.** `message-cp person add <name> --admin` makes an admin person, and a command on the server marks or unmarks an existing person (it changes what their existing tokens may do at once, with no new token). An admin person's token does everything a person token does plus the account's admin actions in the dashboard: today that is deleting a conversation, which a plain person token cannot. It still sends and posts only as that person. The account's full token stops acting as people: `POST /api/send` and `POST /api/post` with it are refused with a message saying to sign in as a person, and the dashboard opened with it reads and does admin actions but offers no "Post as" and says how to sign in as a person to send. Nothing outside the dashboard sends as a person with the full token today (check the end-to-end check and `ops/` when building); it keeps working for MCP, `/wait`, approving clients and scripts as now. `/setup.md` and getting started make the person setting up the server an admin person and sign them in with `login-link --person`.

The parts below make the first run feel like this: the person tells their agent "set up message-cp", ends up in the dashboard as themselves, invites their team from there, and everyone adds agents by pasting the server's address into their client. The server shell is for installing and for recovery, not for day-to-day people or agent tasks.

5. **Setup ends with you signed in as you.** `/setup.md` asks the person's name (one more question, for a team server only), makes them an admin person, and ends by opening the dashboard signed in as them (`login-link --person`, opened on their machine, never shown in chat). The full token stays in the server's configuration for scripts and recovery; setup never signs a browser in with it, and the docs present it as the recovery key, not as a way to use the dashboard.
6. **Invite from the dashboard.** An admin person can add a person (plain or admin) and get an invite link for them from the dashboard, with no server shell. An invite link works once, lasts days rather than minutes (pick a default, such as 7 days, and say it on the page), and opening it signs that browser in as that person. An admin can make a new link for an existing person who lost access, and see and cancel unused invites. Like login codes, only a hash is stored and a used, expired or cancelled link says so plainly. `person add` and `login-link` on the server keep working.
7. **One way to connect an agent: paste the address and approve.** `/setup.md` section 4 and getting started lead with MCP's OAuth flow for every client that supports it (check Claude Code, Codex, Claude Desktop, claude.ai and Cursor against their current docs and by a real run where the client can be run), so connecting an agent is adding the server's `/mcp` address to the client and approving in the dashboard. `connect`, the connect file and `init --from` stay as the fallback for clients that cannot do OAuth, described in a few lines after the main path. Waking: a client that keeps its own OAuth token uses `wait_for_mail`, as Codex does now, unless a simpler way exists.
8. **One approved client, many agents.** When approving a client, the person can choose "this client registers its own agents" instead of naming one agent. The token the client gets then lets each of its sessions call `register` with a new name, as agents on one machine do, so several Codex or Claude Code sessions on one machine are each their own agent from one approval. It can register only names no agent or person of the account has, and act again only as the agents it registered itself (so a restarted session can take its name back); never as another client's agent or a person. The dashboard's approved clients list shows such a client as able to register agents and lists the agents it registered; revoking the client ends them all. Approving a client as one named agent (part 3c) stays the default and works as now.
9. **An admin page in the dashboard.** An admin person sees one page for running the account, so nothing day to day needs the server shell: people (add, make or unmake admin, remove, and their invites from part 6), tokens (list with kind, who or what each is for and when it was made and last used; revoke; make a read-only or agent token, shown once with a copy button and never again), agents (list, remove, reset a key), approved clients (revoke) and webhooks (list, add, remove; a secret or header value is shown once when added and never again). Every action asks for confirmation when it cannot be undone, and says what it ended (for example "revoked: this also signed out 2 browsers"). A browser's sign-in is its own session, not the raw token: an opaque id stored only as a hash, which the page can list and end per browser, and which ends when its token is revoked. A plain person, viewer or agent never sees the page and the server refuses its actions (403). It works within the admin's own account only. The server commands keep working and stay the way to make accounts and to recover when no admin can sign in.

Who it is for (above) says a team server has "an account and token per person"; for a team that means one account with a token per person, and this goal makes that true.

## Previous goal (done): setting up is one prompt

Most people will meet message-cp by telling their coding agent (Claude Code, Codex, Cursor) "set up message-cp" and pointing it at the site. After this goal that works: the agent finds one page written for it, asks the person only what it cannot decide, sets message-cp up, proves it works and says what it did, and the person never has to read the docs. The docs also become short: today the site is about 22,000 words, most of it reference written for completeness. A person should be able to read everything they need in a few minutes.

Build as if message-cp were published to npm as `message-cp`, but do not publish it: the owner publishes when they decide to launch. Docs and setup steps use `npx -y message-cp` (and `npm install -g message-cp`) as the install, not a clone and build. Until launch they cannot be run by a stranger; verify them with a package built by `npm pack` instead. Parts 1 and 3 touch different files and can be built at the same time; part 2 needs part 1, and part 4 comes last.

1. **The package is ready to publish.** `npm pack` produces a package that, installed from the tarball, gives the `message-cp` command, and `claude mcp add message-cp -- npx -y message-cp` (or the equivalent for the other clients) starts the stdio server with no other argument, path or clone. `npm publish --dry-run` passes, the package holds only what it needs to run (no tests, site, factory or ops files), and `private: true` is removed. Nothing is published.
1b. **One command sets up a client.** `npx -y message-cp init` (as AgentDM's `npx agentdm init` does for its service) detects which coding agents are installed (Claude Code, Codex, Cursor, Claude Desktop), asks which to set up if more than one, adds message-cp to that client's MCP configuration for this machine, then proves it works by registering a test agent, sending it a message and reading it back, and prints in a few lines what it changed and how to undo it. Run again, it changes nothing that is already set up. With `--url` and an agent token it sets the client up for a team server instead. It never prints a token or key. `setup.md` uses it as the main step, with the manual commands as the fallback. Build it after part 1 and before part 2.
2. **A setup page for agents.** `/setup.md` on the site: numbered steps an agent follows, in plain imperative sentences. It asks the person at most two questions (just this machine or a team server, and for a team server, where it runs and on what domain), then gives the exact commands for each client, then has the agent prove it works (register, send itself or a second agent a message, read it back), then tells the person in a few lines what was set up and how to add another agent. It covers one machine, a team server with `serve`, and Docker. It is short: under about 1,000 words. `/llms.txt` points to it first. The landing page's main action becomes a prompt to copy, such as "Set up message-cp for me: follow https://message-cp.vercel.app/setup.md", with the manual one-line install under it.
3. **Short docs for people.** Every page is brief and easy to skim: short sections, tables and lists over paragraphs, no walls of text. The comparison page is a plain comparison (a table and a line or two per product, with sources), not an argument for message-cp. The whole site, `setup.md` and `llms.txt` included, comes to under about 6,000 words. Each page says only what a reader needs to use message-cp, in the fewest words that are still true; detail an agent already gets from the server itself (tool and parameter descriptions, the server's instructions) is not repeated on the site, and the reference links to where it lives instead. Getting started is one page a person reads in two minutes. Every claim that stays is still true of the code, as AGENTS.md requires: shorter, never vaguer or wrong. Where AGENTS.md names a section or page that moves or goes (the reference's "Limits" and "Database" sections, `site/src/pages/tools.astro`, `server.astro` and the others it names), the pull request updates those pointers in AGENTS.md to where the content now lives.
3b. **The token is the agent.** Today a team-server client needs three headers: the token (which only names an account) plus `X-Message-CP-Agent` and `X-Message-CP-Agent-Key`, or else the agent calls `register` with its key, which puts the key in the model's context. Some clients cannot send custom headers from their own setup commands (`codex mcp add` takes only a bearer token), so `init` refuses them. After this part, `connect` makes an agent token bound to that one agent, and that token alone is the agent's credential: a client sends only `Authorization: Bearer <token>`, every session with it acts as that agent from its first request with no `register` and no key, `GET /wait` with it answers only for that agent, and the token cannot register or act as any other name. `init`, `init --from` and `/setup.md` use the bound token, so every client that can send a bearer token works, Codex included. Unbound agent tokens and the name and key headers keep working for existing setups, per the guardrail on migration paths. Build this before part 4, so the fresh agent tests the simple path.
3c. **Adding message-cp from any MCP client, through MCP's OAuth flow.** A person pastes a team server's `/mcp` address into Claude (claude.ai, Claude Desktop), ChatGPT, Claude Code, Codex (`codex mcp add ... --url` then `codex mcp login`) or any client that follows the MCP authorization spec, approves in the browser, and the client is connected as an agent, with no token copied anywhere and no command run on the server. The server follows the MCP authorization specification for an HTTP server: it publishes OAuth protected-resource metadata (RFC 9728) and points to it from its 401 responses, acts as its own authorization server with RFC 8414 metadata, requires PKCE with S256, and registers clients through Client ID Metadata Documents and Dynamic Client Registration (RFC 7591), since current clients use one or the other; check the current spec at modelcontextprotocol.io and each client's docs when building. The authorization page is part of the dashboard: the person signs in with a token of the account that may approve (the full token until person tokens exist), sees the client's name and where it will send the result, chooses or confirms the agent's name, and approves or refuses. What the client receives is an agent token bound to that agent (part 3b), revocable like any other; refresh tokens only if a client needs them. Static tokens and `connect` keep working for clients and scripts that send a bearer token; `init --url` and `/setup.md` use this flow as their main team-server path once it exists. Codes and requests are single-use and short-lived, redirect addresses are checked exactly against what the client registered, and nothing is ever printed or logged that would let someone else complete an approval. Build this before part 4.
4. **Proof from a fresh agent.** A coding agent with none of this project's context, given only the prompt from the landing page and a package built by `npm pack` standing in for npm, sets message-cp up on one machine and, separately, as a Docker team server on `localhost`, and proves each works. Every place it got stuck or had to guess becomes a fix. The pull request or ticket carries its transcript or a summary of each step and what it saw.

## Previous goal (done): agents hold a conversation without glue

Today an agent that needs an answer from another sends a message, starts a background shell loop to be woken, reads its inbox, and works out by itself which message answers which. That glue is the main friction in using message-cp, and the factory's own agents hit it every day. After this goal, asking another agent something is one tool call, every MCP client can wait for mail without a shell, and replies say what they answer. Parts 1 and 3 touch different code and can be built at the same time; 2 and 4 build on 1, and 4 also on 3. Each part is a ticket of its own or more.

1. **Replies say what they answer.** Every direct message has an id that `read_inbox`, `read_conversation` and `search` return, and `send_message` takes an optional `in_reply_to` with the id of a direct message the sender received. The reply carries it, and the reading tools return it, so an agent handling several requests answers each one by id. `in_reply_to` must name a message in the sender's own account that was sent to the sender; anything else fails clearly. Messages sent without it behave exactly as now, and existing messages read as having no reply link.
2. **The sender can see whether a message was read.** `send_message` also returns the id of each message it created (a broadcast stores one message per recipient, so it returns one id per recipient). A `message_status` tool takes such ids and returns, for each, the recipient and whether and when it was read, from the `read_at` the server already records when `read_inbox` returns a message (the same state as the dashboard's read receipts). A caller can only ask about messages it sent; any other id fails without saying whether it exists.
3. **Waiting for mail without a shell.** A `wait_for_mail` tool holds the call open until the caller has unread mail, unread posts in a channel it joined, or an unread mention, or until a timeout the caller gives (capped, with a default), and then returns what the `wait` command prints, without reading or marking anything. A held call counts against a cap checked before the hold begins, like `/wait`, and gives its slot back when it ends. This is for clients that cannot run a background command (Cursor, Claude Desktop); the `wait` command stays for those that can.
4. **Asking in one call.** An `ask` tool sends a direct message to one agent and waits, up to a timeout the caller gives (capped, with a default, and counted like part 3's hold), for that agent's reply to it (a message with `in_reply_to` set to the question's id). It returns the reply, or says plainly that none came in time and gives the question's id so the caller can look for the answer later. The reply is marked read when `ask` returns it, as `read_inbox` would. The tool descriptions tell a receiving agent to answer with `in_reply_to`, so that `ask` sees the answer.

## Previous goal (done): seeing agents work, and keeping their names

When the owner messages an agent, the dashboard should show what is happening before the reply arrives, and an agent whose key is lost should be recoverable without losing its history. In this order, each part a ticket of its own or more:

1. **Read receipts.** The dashboard shows under a direct message (and on a post's mentions) whether the recipient has read it, from the read state the server already records when `read_inbox` returns a message, so "read" means the agent has picked it up. It needs nothing from agents and works for every agent. It never marks anything read itself.
2. **"Starting…" for agents a message starts.** When a direct message to an agent has a webhook delivery that the receiver accepted (a 2xx), and the agent has not read the message yet, the conversation shows the agent as starting, so a person messaging `planner` or `status` sees at once that a run is on its way. It shows nothing for agents without such a webhook, and nothing once the message is read.
3. **An agent can say what it is doing.** A tool lets a registered agent set a short status line about its own work (for example "reading Linear"), which the dashboard shows next to its name and in its open conversations, and which clears itself after a few minutes, when the agent sets another, when it replies, or when it unregisters. An agent can only ever set its own. The factory's runs set it as they work (this part touches the owner's factory files for the instructions, and is the owner's to wire).
4. **The owner can reset a lost key.** `message-cp agent key reset <name> [--account <account>]` on the server gives a registered agent a new key, prints it once, and keeps the agent's messages, mentions, channel read positions and webhooks. The old key stops working at once, and every session currently acting as the agent is ended (as `agent remove` ends them, but the agent and its history stay), so a key reset after a leak cuts off whoever had it; the agent's own sessions register again with the new key. It never applies to people or another account's agents, and prints nothing but the new key and which agent it belongs to.

5. **Agent tokens, which cannot act as a person.** `message-cp token add <account> --agent-only` makes a third kind of token besides full and read-only. It can do everything an agent does (`/mcp`, `/wait`, every read-only `GET /api/*`, and deleting a direct conversation, which the end-to-end check's clean-up may need: confirm how `npm run e2e` cleans up) but gets 403 on the two routes that act as a person, `POST /api/send` and `POST /api/post`, and the dashboard treats it like a read-only token for posting. `token list` shows each token's kind; existing tokens and `MESSAGE_CP_HTTP_TOKEN` keep working exactly as now. This is why: today the factory's runs hold a full token, so a run talked into it by text it reads could post as the owner and ask `planner` for work, which the factory would build and deploy. With agent tokens in the factory's environments, only tokens a person holds can act as one.
6. **A connection can carry its agent's identity.** An MCP client can name its agent and key in the connection's own configuration (for example `X-Message-CP-Agent` and `X-Message-CP-Agent-Key` headers on the HTTP connection, the key filled in from an environment variable by the client), and then every session it opens acts as that agent from its first request, with no `register` call: a client that reconnects with a new session after a dropped connection, a server restart or a long sleep is still that agent. This is why: COL-99 restores a session only when the client resends its old session id, and Claude Code (so every factory run) opens a new session instead, so after a restart its agent is unregistered again. Every check `register` makes still applies to a header (the key must match, the agent must be in the token's account, a person's name is refused), a wrong or missing key fails the request clearly rather than leaving the session unregistered, and nothing logs the key. Calling `register` still works as now for clients that do not set the headers.

The previous goal, a tidy account and agents you can call (removing agents and conversations, e2e cleaning up, registrations surviving restarts and waits, webhooks with a header, a limit and a fixed body, and the standing `planner` and `status` agents a message starts), is done, as are clickable links, the dashboard redesign, people taking part, the dashboard itself, read-only tokens, mentions, search, outgoing webhooks, channels and the open-source package.

Account separation is the one security boundary that matters most here: a change that could let one account read, send as, list, wake on or remove another account's agents or messages is wrong, however small.

## What "production ready" means here

1. **It does not lose messages.** The database is backed up nightly off the server, and a restore has been tested.
2. **What is on `main` is what is running.** A merge reaches the server within minutes, is checked there, and is rolled back automatically if the check fails.
3. **Breakage is noticed by a machine, not by the owner.** A daily check uses the live server the way an agent does and files a ticket when it fails.
4. **The owner is not needed day to day.** Tickets are written, built, reviewed, merged and deployed by the factory. The owner reads a weekly summary.

## Guardrails

- Never break a working agent's setup without a migration path: old names, paths and settings keep working for at least one release after a change.
- Messages and tokens are private. Nothing logs a message body or a token, and no check posts one anywhere.
- Changes to this file, to `tessl.json`, to `tessl-factory/`, and to the code review policy (`.tessl-code-review.yml` and `review-lenses/`, which a pull request is reviewed with its own copy of) are the owner's. The factory may propose them but never merges them. `AGENTS.md` is the factory's: it may add to, change or remove its guidance, and merges that itself like any other change.
- Prefer removing code to adding it. A feature needs a reason an agent hits in practice, not a reason it might.
- At most three factory tickets are in flight at once.

## Not now

- Sign-in of any other kind built into the server (GitHub, Google, passwords, single sign-on). The server's only OAuth role is the MCP authorization flow above, which issues its own agent tokens after a person approves with a token.
- A web page for managing the server's accounts, or anything beyond the admin page of the current goal's part 9. Everything else is managed with the command on the server; the dashboard writes nothing except what a person posts or sends, the direct conversations a person deletes, a person's approval of a client's authorization request (part 3c), and an admin person's management of their own account's people, invites, tokens, agents, approved clients and webhooks (current goal, parts 6 and 9). Accounts are still managed only on the server.
- Publishing to a container registry. Publishing to npm is the owner's: a release workflow publishes `message-cp` when the owner pushes a version tag (`v<version>`, matching `package.json`) on `main`, and only the owner may create those tags. The same workflow also publishes the server's listing (`server.json`) to the official MCP Registry, and after each release a loop drafts the GitHub release notes for the owner to publish. When the owner asks for a release (a ticket, or a message to the planner) naming the version, the factory prepares it: one pull request that bumps the version everywhere it is recorded (`package.json`, `package-lock.json`, `server.json`) and changes nothing else. Only the owner decides when to release and pushes the tag. The factory may build and change the release workflow, but never bumps the version unasked, pushes a tag, publishes, or publishes a release.
- New kinds of content beyond messages (files, memories, tasks). Channel posts are messages; pinned or editable posts, threads of channel posts, reactions and per-channel permissions are not now either. A direct message saying which message it answers (done) is not a thread view: nothing groups or nests messages.
